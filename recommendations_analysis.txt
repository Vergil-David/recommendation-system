РЕФАКТОРИНГ INTERACTIONS У PageStream: МОДЕЛЬ USER MOVIE STATE

1. Що саме змінено

У recommendation MVP не переписувалась архітектура.
Збережено той самий layered підхід:
handler -> service -> repository -> database

Також не змінювались:
- auth;
- users;
- friends;
- movies;
- базові recommendation endpoints.

Змінено лише interaction model.
Замість занадто спрощеної схеми `view | like | skip` система тепер працює з повноцінним набором user movie states:
- `viewed`
- `liked`
- `disliked`
- `favorite`
- `skipped`

Для сумісності старі значення теж приймаються:
- `view` -> `viewed`
- `like` -> `liked`
- `skip` -> `skipped`

2. Чому Like/Skip було недостатньо

Стара модель була придатна тільки для дуже грубого MVP, але вона змішувала різні наміри користувача в надто малу кількість сигналів.

Основні проблеми старої моделі:

1. `like` не покривав усі позитивні сценарії.
   Користувач може:
   - просто схвалити фільм як recommendation signal;
   - хотіти зберегти його в особисту бібліотеку;
   - уже подивитися фільм і тільки потім оцінити його.
   У старій схемі це все зливалося в один тип.

2. Не було окремого явного негативного сигналу.
   `skip` означав "пропустив", але не давав відповіді, чи це:
   - тимчасово нецікаво;
   - фільм не сподобався;
   - користувач свідомо не хоче такого типу контенту.

3. Не було нейтрального стану перегляду.
   Відкриття сторінки фільму або факт перегляду сам по собі ще не означає позитивної оцінки.
   Системі потрібен окремий state `viewed`, який не є лайком.

4. Неможливо було коректно відокремити "подобається" від "хочу зберегти".
   Для PageStream це різні продуктові сценарії:
   - recommendation feedback;
   - personal library / save-for-later behavior.

Отже, стара трійка `view/like/skip` давала занадто мало семантики для подальшого розвитку recommendation logic.

3. Чому додано саме viewed / liked / disliked / favorite / skipped

Новий набір станів обрано тому, що він покриває найтиповіші сценарії користувача без зміни архітектури та без переходу до event-sourcing.

Кожен стан має окремий зміст:

- `viewed`
  Користувач відкрив або вже бачив фільм.
  Це нейтральний behavioral signal.

- `liked`
  Користувач явно дав позитивний feedback.
  Це основний легкий позитивний recommendation signal.

- `disliked`
  Користувач явно дав негативний feedback.
  Це сильніший негативний сигнал, ніж простий пропуск.

- `favorite`
  Користувач додав фільм у власну бібліотеку.
  Це не просто "подобається", а "хочу зберегти / повернутися до цього фільму".

- `skipped`
  Користувач не хоче отримувати цей фільм у рекомендаціях зараз.
  Це exclusion signal.

Такий набір є достатньо багатим для MVP і водночас не ламає існуючий repository/service/backend shape.

4. Як тепер зберігаються interactions

Таблиця `interactions` не видалялась і не замінювалась іншою.
Зберігається той самий принцип:
- один актуальний запис на пару `(user_id, item_id)`.

Але тепер у записі підтримуються окремі state-поля:
- `viewed`
- `liked`
- `disliked`
- `favorite`
- `skipped`

Поле `interaction_type` залишене як поточний останній canonical type.
Це корисно для сумісності, міграції старих даних і плавного переходу існуючого MVP.

5. Як мігруються старі дані

Міграція зроблена без видалення наявних interaction rows.

Старі значення переводяться так:
- `view` -> `viewed`
- `like` -> `liked`
- `skip` -> `skipped`

Також backfill заповнює нові boolean state-поля на основі старого `interaction_type` та `is_liked`.

Важливо:
- старі записи не видаляються;
- primary/unique logic не руйнується;
- таблиця залишається сумісною з поточним backend flow.

6. Як кожен state впливає на рекомендації

6.1. `viewed`

Вплив:
- означає, що фільм уже був відкритий або побачений користувачем;
- не є позитивним джерелом для similarity search;
- використовується для exclude-set, щоб не крутити той самий already seen movie знову.

Тобто `viewed` - це нейтральний signal з ефектом виключення.

6.2. `liked`

Вплив:
- є позитивним recommendation signal;
- використовується як source item для content-based similarity;
- також входить до exclude-set, щоб той самий фільм не рекомендувався назад.

Тобто `liked` одночасно:
- допомагає знаходити схожі фільми;
- блокує повторну рекомендацію самого source item.

6.3. `disliked`

Вплив:
- є явним негативним feedback signal;
- не використовується як source item;
- входить до exclude-set.

Для MVP це означає: фільм не повертається в рекомендації і не бере участі в позитивному similarity-побудуванні.

6.4. `favorite`

Вплив:
- розглядається як сильний позитивний інтерес;
- використовується як source item для content-based similarity разом із liked items;
- входить до exclude-set, бо немає сенсу рекомендувати назад те, що вже збережено в personal library.

Отже, `favorite` одночасно:
- посилює персоналізацію;
- працює як ознака "цей фільм уже важливий для користувача".

6.5. `skipped`

Вплив:
- означає "не показувати знову";
- не використовується як позитивний source item;
- входить до exclude-set.

У поточному MVP `skipped` працює як прямий сигнал виключення з рекомендаційної стрічки.

7. Чому favorite і liked - це різні стани

`liked` і `favorite` не можна повністю зливати в один тип, бо вони мають різний продуктовий сенс.

`liked` означає:
- фільм сподобався;
- це quick positive feedback;
- це простий recommendation signal.

`favorite` означає:
- фільм користувач хоче зберегти у власну бібліотеку;
- це stronger intent;
- це не тільки feedback для моделі, а й окремий user-library сценарій.

Іншими словами:
- `liked` = "мені це подобається";
- `favorite` = "це важливий для мене фільм, я хочу його зберегти".

Користувач може поставити `liked` без `favorite`.
Користувач також може мати `favorite` як окрему дію з вищим рівнем наміру.

Саме тому в API states повертаються окремими boolean полями, а не одним enum без контексту.

8. Як це впливає на endpoint `POST /interactions`

Endpoint тепер приймає canonical values:
- `viewed`
- `liked`
- `disliked`
- `favorite`
- `skipped`

Але для backward compatibility ще приймаються:
- `view`
- `like`
- `skip`

Це важливо, щоб існуючий frontend не ламався під час переходу.

9. Новий endpoint для читання станів

Додано endpoint:
`GET /interactions/items?ids=id1,id2,id3`

Він повертає current state map по item_id.
Це потрібно фронтенду, щоб:
- позначати already viewed items;
- показувати активний liked/favorite/disliked/skipped state;
- не будувати UI на припущеннях;
- синхронізувати картки фільмів з бекендом.

10. Як тепер працює `GET /recommendations`

Алгоритм залишився content-based, але став точнішим по signals.

Тепер:
1. Бекенд читає позитивні source items із `liked` і `favorite`.
2. Для них виконується pgvector similarity search.
3. Негативні сигнали `disliked` і `skipped` не беруть участі в побудові similarity, але жорстко блокують повторну рекомендацію цих фільмів.
4. Окремо збирається exclude-set з усіх фільмів, що мають будь-який активний interaction state:
   - `viewed`
   - `liked`
   - `disliked`
   - `favorite`
   - `skipped`
5. Similar items агрегуються.
6. Якщо personalized results недостатньо або їх немає зовсім, додається fallback на popular/newest movies.
7. Fallback також поважає той самий exclude-set, тому вже відомі користувачу фільми не повертаються назад.

Отже, логіка рекомендацій не переписувалась, але стала більш виразною завдяки кращим user signals.

11. Як тепер працює `GET /recommendations/friends`

Friend-based endpoint не ламається і залишається окремим recommendation layer.

Він базується на позитивних social signals друзів:
- `liked`
- `favorite`

Логіка така:
1. Система знаходить accepted friends поточного користувача.
2. Для цих friend_id читаються всі positive movie states:
   - `liked`
   - `favorite`
3. Кандидати агрегуються по item_id.
4. Для кожного item рахується social support:
   - скільки друзів його лайкнули;
   - скільки друзів зберегли його у favorite;
   - скільки унікальних друзів загалом підтримують цей item позитивним сигналом.
5. Потім застосовується той самий user exclude-set:
   - `viewed`
   - `liked`
   - `disliked`
   - `favorite`
   - `skipped`
6. У відповідь повертаються top items з social reason, наприклад:
   - `Liked by 3 of your friends`
   - `Saved by your friends`
   - `Liked by 2 of your friends and saved by 1 of them`

Отже, friend-based recommendations тепер використовують не тільки лайки друзів, а весь позитивний friend intent, не порушуючи існуючу friends architecture.

12. Чому це рішення добре підходить поточній архітектурі PageStream

Причини:

1. Не потрібно переписувати auth/users/friends/movies.

2. Не потрібно змінювати базову структуру recommendation service.

3. Міграція є additive і безпечна для наявних даних.

4. Repository layer залишається єдиною точкою доступу до interaction state.

5. Frontend може перейти поступово, бо старі `view/like/skip` ще приймаються.

6. Система отримує кращу семантику сигналів без переходу до складнішої ML-платформи.

13. Висновок

Refactor interactions у state-based модель є правильним кроком для поточного етапу PageStream.

Він вирішує головну проблему старого MVP:
`like/skip` було занадто мало, щоб якісно розділити нейтральну, позитивну, негативну та library-поведінку користувача.

Нова схема:
- точніше описує намір користувача;
- не ламає існуючу архітектуру;
- зберігає backward compatibility;
- покращує exclude logic;
- дає кращу основу для наступних recommendation improvement кроків.

Тобто це не переписування системи, а правильне еволюційне посилення interaction layer усередині вже існуючого PageStream backend.

14. Як перевіряти вручну

Для manual check достатньо пройти такий сценарій:

1. Поставити `liked` одному фільму.
   Потім викликати `GET /recommendations` і перевірити, що:
   - сам лайкнутий фільм не повертається;
   - у стрічці з'являються схожі фільми;
   - у response є `score` і `reason`.

2. Поставити `favorite` іншому фільму.
   Після цього `GET /recommendations` має:
   - не повертати сам favorite movie;
   - використовувати його як ще один positive source для similarity.

3. Поставити `disliked` фільму.
   Після цього:
   - фільм не повинен з'являтися в `GET /recommendations`;
   - фільм не повинен з'являтися у fallback-підбірці;
   - `disliked` не повинен використовуватися як source item.

4. Поставити `skipped` фільму.
   Після цього:
   - фільм не повинен з'являтися повторно;
   - він має бути тільки exclusion signal, а не positive source.

5. Відкрити фільм і записати `viewed`.
   Після цього перевірити, що він також не повертається в персональних рекомендаціях.

6. Для `GET /recommendations/friends`:
   - нехай один accepted friend поставить `liked` фільму;
   - інший accepted friend поставить `favorite` тому самому або іншому фільму;
   - endpoint має врахувати обидва типи позитивних friend signals;
   - reason повинен відповідати типу social support.

7. Повторно викликати `GET /interactions/items?ids=...` для тих самих item_id і перевірити, що states у відповіді збігаються з очікуваними boolean flags.
